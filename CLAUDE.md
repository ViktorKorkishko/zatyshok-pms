# zatyshok-pms — контекст проєкту для Claude Code

## Що це
Типова інформаційна система для мережі готелів «Затишок» (PMS + портал онлайн-бронювання).
Навчальний проєкт — комп'ютерний практикум з дисципліни «Проєктування і розроблення ІС та технологій»
(КПІ, кафедра ІСТ, група ІТ-61м). Команда: Коркішко Віктор, Геневський Максим. Обидва — C#-розробники
без досвіду у веб-розробці та готельній предметній області: пояснюй рішення коротко, не припускай знання React/EF Core.

Повна специфікація (вимоги FR-xx/NFR-xx, сценарії UC-xx, моделі станів, архітектура, сутності БД) —
у папці `docs/` (файли 01–07 .md, українською), у git. ЗАВЖДИ читай відповідний
розділ перед реалізацією: 03 — вимоги і статуси, 05 — сценарії, 07 — архітектура і перелік сутностей.

## Архітектура (рішення прийняті, не міняти без обговорення)
- **Модульний моноліт** на ASP.NET Core 8. Один деплой, чіткі межі модулів, одна БД PostgreSQL.
  Мікросервіси/брокери повідомлень — НІ. Доменні події — усередині процесу; листи — через Outbox-таблицю.
- Проєкти: `src/Zatyshok.Domain` (сутності, enum-и статусів, доменні правила, без залежностей),
  `src/Zatyshok.Infrastructure` (EF Core, DbContext, міграції, репозиторії/сервіси доступу до даних),
  `src/Zatyshok.Api` (контролери, DTO, автентифікація, Swagger), `src/Zatyshok.Worker` (фонові завдання),
  `tests/Zatyshok.Tests` (xUnit). Залежності: Api/Worker → Infrastructure → Domain. Ніколи не навпаки.
- Модулі всередині Api/Domain: Identity, Rooms (номерний фонд і тарифи), Bookings, FrontDesk (заселення/виселення),
  Guests, Housekeeping, Billing, Reporting, Notifications, Audit. Папка на модуль: `Modules/<Name>/`.
- Клієнти: `web/staff` (робоче місце персоналу), `web/guest` (портал гостя) — React + TypeScript + Vite,
  REST через `/api`, JWT. UI-бібліотека обирається окремим рішенням (не додавай без запиту).
- Доступ = роль + область видимості (HotelId або вся мережа). Перевірка на сервері для кожного запиту.

## Стек і команди
- .NET 8 SDK, EF Core + Npgsql, PostgreSQL 16 (локально — Docker), xUnit, Swashbuckle.
- Node 22, npm; `web/*`: `npm install`, `npm run dev`, `npm run build`, `npm run lint`.
- Збірка: `dotnet build` з кореня. Тести: `dotnet test`. Запуск API: `dotnet run --project src/Zatyshok.Api`
  (http://localhost:5084, Swagger на /swagger).
- Міграції: `dotnet ef migrations add <Name> --project src/Zatyshok.Infrastructure --startup-project src/Zatyshok.Api`.
- Перед комітом: `dotnet build` має бути без помилок, `dotnet test` — зеленим.

## Доменні правила (з docs/03, розділ 6.2.1) — порушення = баг
- Бронювання робиться на КАТЕГОРІЮ номера; конкретний номер призначається при заселенні.
- `Booking.RoomId` — nullable FK на `Room`: порожній при створенні, заповнюється при заселенні (UC-12) або при
  попередньому призначенні номера в день заїзду (номер → Reserved). У розрахунок доступності не входить.
  Скасування бронювання з призначеним номером (одна транзакція): статус → Cancelled, `RoomId` → NULL, номер → Free.
  Один номер не може бути призначений двом бронюванням у статусах Confirmed/CheckedIn.
- Доступність = активні номери категорії (крім «на ремонті») − бронювання тієї ж категорії у статусах
  Confirmed/CheckedIn, що перетинаються за датами. Перевірка + вставка бронювання — в ОДНІЙ транзакції
  (запобігання подвійному бронюванню, FR-09, NFR-04).
- Статуси бронювання: New → Confirmed → CheckedIn → Completed; New/Confirmed → Cancelled; Confirmed → NoShow.
- Статуси номера: Free, Reserved, Occupied, Dirty (потребує прибирання), OutOfOrder (на ремонті).
- Статуси завдання на прибирання: New → Assigned → InProgress → Done; Cancelled.
- Статуси рахунку: Open → PartiallyPaid → Paid; Voided.
- Виселення (одна транзакція): бронювання → Completed, номер → Dirty, рахунок закритий, створено HousekeepingTask.
- Переселення заселеного гостя (UC-06/А3, FR-21) — єдина зміна `RoomId` після заселення, одна транзакція:
  старий номер → Dirty + HousekeepingTask типу «після виїзду»; новий номер (має бути Free, не Dirty) → Occupied;
  `RoomId` оновлено; у `BookingHistory` — старе й нове значення та причина від оператора. Дозволено лише в номер
  тієї самої або вищої категорії; тариф і категорія бронювання не змінюються, рахунок не перераховується.
- Завершення прибирання після виїзду → номер Free.
- `Guest.UserId` — nullable FK на `User` з унікальним індексом (1:1, необов'язковий з обох боків). Гість із порталу
  має обліковий запис, гість із телефонного бронювання — ні; персонал профілю гостя не має. Самореєстрація
  прив'язується до наявного профілю за поштою лише після її підтвердження листом; у кабінеті гість бачить запит
  «це ви?» з кнопкою «Це не я» → зв'язок розривається, створюється порожній профіль, пошта в старому профілі
  стає непідтвердженою. Сценарію злиття дублікатів у першій версії немає (FR-24, UC-09/А1).
- Одна роль на користувача: `User.RoleId` — FK, без таблиці зв'язку. Разом 18 таблиць.
- Сутності майже не видаляються фізично: скасування/деактивація/блокування + історія змін і журнал аудиту.
- Усі дати/час у БД — UTC; дати заїзду/виїзду — календарні дати готелю.

## Конвенції
- Код, ідентифікатори, коментарі в коді — англійською. Повідомлення користувачу (UI, помилки API) — українською.
- Коміти: Conventional Commits англійською (`feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`), короткий підмет.
- Гілки: `feature/<коротка-назва>`, злиття в `main` через pull request. Ніколи не пушити в `main` напряму.
- Один PR — одна задача. Маленькі коміти з осмисленими повідомленнями.
- Не комітити: `.idea/`, `node_modules/`, `bin/`, `obj/`, секрети (`appsettings.*.json` з паролями — через user-secrets або .env).
- Знайдені під час тестування помилки фіксувати як GitHub Issues (опис, кроки відтворення, очікуваний/фактичний результат).
